# 14 周详细操作手册验收规范

> 生效日期：2026-09-03  
> 适用范围：每周的 `01_FOUNDATIONS.md` 与 `02_LAB_GUIDE.md`。  
> 核心原则：读者拿到一台符合前置条件的机器后，应能只依赖本手册与所链接的官方材料，从空目录走到可检查的实验结果；不能要求读者猜测仓库结构、补写关键代码或自行选择数据版本。

## 1. 什么不算详细操作手册

以下任一情况都不能通过：

- 只写“实现 BPE / 训练模型 / 跑评测”，没有文件、代码与命令；
- 命令调用 `src.*`、脚本或配置，但正文既未给出创建内容，也未说明它来自哪个固定版本的官方仓库；
- 只给伪代码，却把后续步骤描述成可直接运行；
- 只写数据集名称，没有仓库 ID、文件名、下载方法、许可检查与完整性检查；
- 只写模型名称，没有 checkpoint ID、revision/tag、加载方式和输入输出契约；
- 只给正式训练命令，没有 CPU/单 batch/短步数 smoke test；
- 写“loss 应下降”“效果更好”，没有观测位置、比较方法和失败分支；
- 把计划中的命令、预期数字或用户自述硬件当成已运行证据。

## 2. Foundations 的必备内容

每篇 `01_FOUNDATIONS.md` 至少应包含：

1. **本周问题与最终产物**：要构建什么、为什么做、与前后周如何衔接。
2. **前置知识与环境边界**：读者需要已会什么；公司 V100、个人 5070 Ti、可选 H100 分别承担什么。
3. **数据与模型对象**：正式名称、官方来源、版本固定策略、许可或使用限制、输入样例。
4. **概念推导**：从输入到 loss/指标的完整数据流，不只给名词定义。
5. **张量 shape 与 dtype**：每个关键边界至少给一个带具体数字的 worked example。
6. **核心算法**：公式、变量含义、最小可运行 Python/PyTorch 示例及输出解释。
7. **训练系统联动**：显存组成、计算热点、通信或 I/O、FP16 数值风险、checkpoint 状态。
8. **正确性不变量**：哪些断言一旦失败必须停止正式训练。
9. **失败模式与诊断树**：症状 → 最小检查 → 根因候选 → 修复 → 回归测试。
10. **自检题**：读者应能在不看答案时解释、手算或预测至少一个小例子。
11. **资料链接与核验日期**：优先数据/模型/框架官方一手资料；会变化的事实标注核验日期。

Foundations 可以引用 Lab 中的完整工程代码，但不得用引用替代原理、shape、数值与失败机制的讲解。

## 3. Lab Guide 的必备内容

每篇 `02_LAB_GUIDE.md` 必须按执行顺序给出以下信息。

### 3.1 下载前

- 明确实验在哪台机器运行，以及哪些产物不得离开公司环境；
- 只读探测 Python、PyTorch、CUDA、GPU、磁盘、Git 与网络；
- 复用已有 Conda 环境，不创建新 Conda/venv；
- 先保存 `pip freeze`，依赖变更必须先 dry-run，并说明回滚方法；
- 列出最低磁盘、显存和预计时间；估算不是运行结果。

### 3.2 数据与模型获取

用表格说明：

| 对象 | 官方 ID/仓库 | revision/tag 固定方法 | 实际所需文件 | 许可检查 | 完整性检查 |
| --- | --- | --- | --- | --- | --- |

随后给可复制命令。下载完成后至少检查文件存在、大小/样本数、schema 和 SHA-256。若固定 revision 不能预先可靠给出，手册必须让用户先解析远端 revision，再将解析值写进 manifest；不得编造 commit。

公司网络不可达时，只允许使用获批镜像、预置副本或本机生成的非敏感合成小样本；不得教绕过网络或数据管控。使用合成样本只能通过代码正确性门，不能替代正式结果。

### 3.3 工程创建

- 给完整目录树；
- 每个新建文件都有职责、输入、输出和调用者；
- 若从零实现，正文提供可运行的完整核心文件，或提供明确的 patch 顺序；
- 若复用官方仓库，给 clone 命令、固定 tag/commit、安装方式以及需要修改的精确文件；
- 配置文件必须给完整最小配置，不能只列字段名；
- 命令中出现的每个本地模块、脚本、配置与输入文件此前都已创建或下载。

代码块必须标明文件路径。教学片段若故意省略代码，必须标为“讲解片段，不可直接运行”，并且不能被后续命令依赖。

### 3.4 逐级运行

执行顺序固定为：

```text
静态/格式检查
  → 纯 CPU 单元测试
  → 单样本/单 batch 前反向
  → 20–100 step smoke test
  → checkpoint/resume 等价性测试
  → 有界正式训练
  → 独立 eval
  → 失败注入或 transfer 测试
```

每一步都写明：

- 从哪个目录执行；
- 完整命令和参数含义；
- 预计耗时/显存（标为估算）；
- 正常时能看到什么字段或文件；
- PASS/FAIL/INCONCLUSIVE 条件；
- 失败时下一条最小诊断命令。

### 3.5 证据与恢复

- 日志至少关联 config、code revision、data revision/hash、seed、precision、world size 与 checkpoint；
- 写清 loss/指标曲线如何读取，以及异常曲线分别暗示什么；
- checkpoint 必须区分“仅权重”与“可等价 resume 的完整状态”；
- 给中断后恢复、OOM、NaN/Inf、数据损坏、DDP hang 等本周相关故障的具体恢复步骤；
- 所有尚未由用户运行的命令统一标记为“待执行”，预期输出不能冒充实测输出。

## 4. 每个 Day 的最小模板

每个 Day/阶段不得只有一段任务列表，至少使用下列结构：

```markdown
## Day N：可验收目标

### 为什么做
### 输入与前置检查
### 本日要创建/修改的文件
### 实现（带文件路径的完整代码或固定官方实现）
### 执行命令
### 预期观测（估算/示例，不是实测）
### 验收条件
### 若失败，按什么顺序查
### 当日证据清单
```

如果一日包含多个独立实验，应拆成 `N.1`、`N.2`，每个实验分别闭环。

## 5. 示例：Week 01 的 BPE 段落怎样才算通过

仅写下面三行不通过：

```text
实现 BPE。
pytest -q tests/test_tokenizer.py
python -m src.tokenizer train ...
```

通过版本至少需要先完成这些事实链：

1. 从 `roneneldan/TinyStories` 的哪个 revision 获取哪两个文本文件；
2. 如何记录 resolved revision、文件 SHA-256、字节数、行数与空样本数；
3. `src/tokenizer.py` 中 byte 初始词表、pair 计数、稳定 tie-break、merge rank、encode、decode、save/load 的实现；
4. `tests/test_tokenizer.py` 中 ASCII、中文、换行、空串、保存再加载、相同输入重复训练等测试；
5. 先用内嵌 toy corpus 训练 270 词表，再用 TinyStories 子集训练 1K 词表；
6. 如何检查 `decode(encode(x)) == x`、OOV=0、序列压缩率和 tokenizer 文件 hash 稳定；
7. 正式 tokenizer 失败时，怎样区分 UTF-8、合并顺序、序列化、数据迭代非确定性；
8. 下游 `data.py` 与模型如何使用同一 tokenizer special-token 契约。

只有这些对象都已被定义，`python -m src.tokenizer ...` 才是一条真实可执行的教学命令。

## 6. 跨周复用规则

后续周可以复用前周产物，但必须：

- 写明准确来源，例如 `week07-ddp` 从 Week 06 的哪个冻结 tag/hash 复制；
- 列出本周新增/修改文件及最小 diff；
- 在开始前重跑上周的关键 smoke test；
- 不把“读者应该还留着”当作输入保证；缺失时给恢复或重建命令；
- 版本变化导致旧命令失效时，以当日官方文档核验并更新来源登记。

## 7. 最终人工验收

自动脚本只能检查结构，最终需人工抽查：

1. 随机选择一个空目录，逐条模拟命令依赖；
2. 所有命令引用的路径都可追溯到创建/下载步骤；
3. 所有关键代码没有 `TODO`、`pass`、省略号或“自行实现”；
4. 所有版本号、模型 ID、数据文件名和 API 与固定来源一致；
5. 示例结果明确标为示例/预计，用户实测结果单独记录；
6. 公司环境步骤没有外传、遥测上传、未授权下载或绕过管控。

本规范本身不是课程内容；它是 28 篇核心手册的发布门。

## 1. 结论

采用 **1 个主代理 + 6 个专职子代理**，共 7 个逻辑角色；运行时最多同时启动 3 个子代理。

不为 14 周各建一个 agent。周次是内容分区，不是稳定职责；如果按周建 14 个 agent，公式、证据、隐私和评分标准会重复并逐渐漂移。6 个专职角色覆盖事实、课程、理论、实验、考核、可靠性六种不同判断，能跨周复用。

官方 OpenAI 文档说明，项目级自定义 agent 放在 `.codex/agents/`，每个 TOML 至少包含 `name`、`description`、`developer_instructions`；subagent 适合可并行的独立工作流，但会消耗更多 token。本项目按该正式结构落盘，并用 `.codex/config.toml` 将子代理并发限制为 3。[AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)、[Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)（核验：2026-09-03）。

## 2. 角色与责任边界

| 角色 | 输入 | 唯一责任 | 输出 | 默认写权限 |
| --- | --- | --- | --- | --- |
| 主代理 | 用户需求、状态、所有子结论 | 定义验收、协调写入、解决冲突、最终校验/归档 | 完整交付与状态 | 项目内写入 |
| `source_auditor` | 原始计划、官方资料 | 事实/版本/兼容性与来源核验 | 事实表、冲突和未知项 | 只读 |
| `curriculum_architect` | 目标、时间、前置依赖 | 周顺序、训练门、工作量、迁移证据 | 课程规格 | 只读 |
| `theory_tutor` | 周规格、论文/文档 | 数学、shape、代码和硬件的联合解释 | `01_FOUNDATIONS.md` | 指定文件写入 |
| `lab_coach` | 周规格、环境约束 | 可执行实验、观测、故障树、验收 | `02_LAB_GUIDE.md` | 指定文件写入 |
| `examiner` | 本周目标与常见失败 | 闭卷问题、rubric、答案和回归题 | `03/04` 两份文档 | 指定文件写入 |
| `reliability_reviewer` | 课程候选稿、schema、校验结果 | 安全/事实/版本/命令/题答一致性审查 | 阻断问题清单 | 只读 |

`theory_tutor`、`lab_coach`、`examiner` 只能修改主代理明确分配的互斥文件；最终状态、进度和 `00_INPUT.md` 仅由主代理写。

## 3. 为什么是这六种专业能力

训练专家的失败常发生在不同层，单一“全能作者”容易把层级混在一起：

| 失败层 | 典型现象 | 首要责任角色 |
| --- | --- | --- |
| 事实/兼容 | V100 被误写为不支持 FP16；新 API 被放进 PyTorch 2.1 命令 | source auditor |
| 学习顺序 | 尚未 overfit 就跑 8 卡；基础 LLM 未掌握就进 VLA | curriculum architect |
| 数学/shape | mask、target、时间方向或 loss reduction 错 | theory tutor |
| 实验/系统 | checkpoint 缺 scaler/RNG；计时含 warmup；rank 数据重复 | lab coach |
| 独立表达 | 会照抄但不能解释 trade-off 或 debug | examiner |
| 证据/安全 | 把 smoke 当结论；建议导出公司 trace；题答 ID 不匹配 | reliability reviewer |

这些责任互相复核但不重叠 ownership。

## 4. 内容生产 workflow

```text
需求与当前证据
      │
      ├── source_auditor：事实、版本、兼容矩阵、冲突
      └── curriculum_architect：先修、时间、Gate、迁移证据
                         │
             ┌───────────┴───────────┐
             │                       │
        theory_tutor             lab_coach
       基础与推导               实验与故障树
             └───────────┬───────────┘
                         │
                    examiner
                   问题/答案/rubric
                         │
              reliability_reviewer
           隐私、事实、命令、ID、一致性审查
                         │
                    主代理验收
          校验脚本 → 状态/进度 → 输入归档
```

可并行项：不同周的互斥目录；同一周的 theory 与 lab 初稿。  
必须串行项：先修排序、事实冲突裁决、题目与答案映射、最终状态更新、输入归档。

## 5. 运行时 workflow

每周真实陪跑不是一次性把答案交给用户，而是五段状态机：

1. **Readiness**：10–20 分钟闭卷先修检查，确定 A0/A1 基线。
2. **Contract**：用户写当日 hypothesis、输入/输出 shape、受控变量、失败标准。
3. **Run**：按 dry-run → overfit → reference → precision/resume → scale 推进。
4. **Evidence review**：只读用户允许提供的摘要；区分模型、系统、测量和证据不足。
5. **Oral gate**：先闭卷作答，再最小提示，再 rubric；记录回归日期。

只有当前 Gate 通过才进入下一周。14 周是能力骨架，不是必须准时翻页的日历。

## 6. 教程交付规格

详细发布门以 [`0_basic_training/00_MANUAL_ACCEPTANCE_STANDARD.md`](0_basic_training/00_MANUAL_ACCEPTANCE_STANDARD.md) 为准。Foundations/Lab 必须让读者从空目录走到可检查结果，不能只是把原计划扩写成更多 bullet。所有尚未现场运行的步骤都标记为“待执行”。

每周目录固定四份实质性文档：

| 文件 | 可验收内容 |
| --- | --- |
| `01_FOUNDATIONS.md` | 具体数据/模型对象与官方来源、概念和推导、带数字的 shape/dtype、最小代码、不变量、算法—infra 连接、失败模式、teach-back |
| `02_LAB_GUIDE.md` | 精确 ID/revision/许可、下载与 hash/schema、目录树、逐文件核心实现、CPU 单测→单 batch→smoke→train→eval→resume、日志/性能解读、止损、证据、三类硬件边界 |
| `03_ORAL_EXAM.md` | 至少 20 个稳定 ID 的分层闭卷问题，不泄露答案 |
| `04_REFERENCE_ANSWERS.md` | ID 一一对应，含评分点、误区和追问；明确先答后看 |

共享协议提供统一术语、证据和安全边界；每周文档仍须自包含关键风险，不能只链接模板。

## 7. 硬件与版本决策

- **纠错**：V100 支持 FP16 Tensor Core。NVIDIA mixed-precision 指南明确说明 Volta 引入 Tensor Core，并以 FP16 乘法、FP16/FP32 累加；训练需对小梯度做 loss scaling。[NVIDIA Mixed Precision](https://docs.nvidia.com/deeplearning/performance/mixed-precision-training/index.html)（核验：2026-09-03）。
- **BF16**：课程不把 BF16 作为 V100 默认路径；现场以设备探针为准。
- **公司版本**：PyTorch 2.1 是约束。教程同时链接 2.1 文档与当前文档，但命令必须采用 2.1 可用接口或显式标注版本分支。[PyTorch 2.1 AMP](https://docs.pytorch.org/docs/2.1/amp.html)、[PyTorch 2.1 FSDP](https://docs.pytorch.org/docs/2.1/fsdp.html)（核验：2026-09-03）。
- **CUDA**：若现场是 CUDA 13，不直接重装；先走公司流程。CUDA 13 已移除 Volta 的离线编译和库支持，Volta 构建路径应停留在经验证的 12.x 或已有兼容栈。[CUDA 13 Release Notes](https://docs.nvidia.com/cuda/archive/13.0.0/cuda-toolkit-release-notes/index.html)（核验：2026-09-03）。
- **租用 H100**：不是周任务默认依赖。只有小资源已通过、问题确需规模、预算/停止条件/产物预注册后才进入。

以上是官方能力边界与计划决策，不代表用户设备已经通过探针。

## 8. 隐私架构

公司环境采用“单向输入、原始产物留内”的训练方式：

- 可输入：公开代码、公开数据、小型合成生成器、空白 report/schema、经批准依赖；
- 只留内部：真实训练代码、配置、数据、日志、trace、checkpoint、图片、机器拓扑和性能数字；
- 可在个人环境重新产生：使用公开数据和独立代码跑出的缩小版公开证据；
- 不允许：任何规避公司政策的同步、截图、网盘、邮件、外部 API 或设备转移建议。

教练只基于用户获准提供的抽象文字做诊断，并明确其证据强度有限。

## 9. 可靠性与验收

确定性校验器检查：

- 14 个预期周目录与 56 个固定文件；
- 文件不是空壳，包含核心章节；
- 闭卷问题 ID 与答案 ID 一一对应；
- Markdown 本地链接不悬空；
- 高风险导出表达不会进入教程；
- 周次、标题和日期一致。

内容审查仍需人工/agent 完成，因为脚本无法判断公式是否正确、命令是否适配现场或结论是否过度。
